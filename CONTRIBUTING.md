# Contributing to Glyt

Glyt is being built as a collaborative discovery project.

You do not need to be a compiler engineer to contribute.

## What can you contribute?

### Language design

You can propose grammar, syntax, typing, abstraction, control, modules, diagnostics, interoperability, or entirely different approaches to programming.

### Human experience

Glyt actively needs insight from people who understand learning, accessibility, education, interface design, writing, creativity, music, games, visual thinking, and other human domains.

### Research

Compare existing languages, study programming education, investigate usability, analyze failure modes, run experiments, or bring evidence that challenges an existing assumption.

### Documentation and examples

A good explanation can be as important as a good implementation.

### Technical work

When implementation begins, contributors will be able to work on tools, language services, frontends, integrations, experiments, and eventually implementations of the language.

## How contribution works

There is no single required way to participate. Someone might open a discussion, share research, propose a design, improve documentation, create an experiment, report a problem, or eventually contribute implementation work.

For substantial changes, a useful contribution usually makes clear:

- what problem or opportunity it is addressing,
- what the contributor is proposing,
- what evidence or reasoning supports it, and
- what trade-offs or unanswered questions remain.

Small contributions are welcome. A correction, useful example, uncomfortable question, or piece of evidence can change the direction of a project just as much as a large code change.

For code changes, branches and pull requests keep proposed work separate from the default branch and make review easier.

## A special rule for technical language

Glyt is explicitly welcoming to people at different levels of technical knowledge.

Do not hide a proposal behind jargon when plain language would work.

For example, instead of only writing:

> “Decouple the elaboration phase from monomorphization in the semantic IR.”

also explain:

> “These two compiler steps are currently too tangled together. Separating them would make each part easier to change independently.”

Technical precision remains important. Clear explanation is part of that precision.

## Disagreement is useful

A contributor is allowed to challenge the founder, the current Constitution, or an existing design.

Strong disagreement should come with reasoning, evidence, experiments, or a concrete alternative when possible.

The default goal is not to make one side win. The default goal is to discover whether a better design can satisfy the legitimate concerns on both sides.

## Changing the Constitution

The Constitution is strong guidance, not sacred text.

If contributors have substantial evidence that an existing principle is wrong, incomplete, or inferior to a better alternative, the principle may be changed.

A constitutional change should answer:

- What is wrong with the current principle?
- What evidence supports the change?
- What new principle or wording is better?
- What important capability or human value does it preserve?
- What trade-offs does it introduce?

## What makes a contribution valuable?

A contribution does not become valuable merely because it is large, technical, or visible.

Useful contributions make the project clearer, more capable, more understandable, more usable, safer, more evidence-based, or more alive.

A smaller contribution that prevents a major mistake can be more important than a large contribution that adds complexity without value.

Glyt is not a contest for ownership of ideas. Credit should remain accurate, but the deeper goal is for good ideas to survive, improve, and become real.

## What we are not looking for

Do not contribute changes merely to accumulate GitHub activity, add unnecessary complexity, collect credit, or make the repository look busy.

Glyt is not a competition to produce the most code.
