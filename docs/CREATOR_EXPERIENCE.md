# Creator Experience

This document describes the intended experience rather than a final UI flow.

## Starting

A person should be able to arrive with an idea even when they know little about programming.

The first meaningful action should move them toward their goal, not toward memorizing a language manual.

## Expanding the idea

Before implementation, the user may need to clarify the idea itself.

Glyt should help that process become concrete through ordinary language, examples, visual feedback, direct manipulation, and understandable programming concepts as appropriate.

## Making

The system should provide a path from the user's current understanding to a working result.

Different users may take different paths toward the same result.

## First failure

Errors should feel like information, not punishment.

The ideal diagnostic communicates:

- what Glyt thinks the user is trying to do
- what went wrong
- why it went wrong
- how the user can change it
- what deeper concept is involved, when useful

## First success

When something works, Glyt should:

- show the result
- explain what happened when useful
- acknowledge the successful creation
- offer meaningful next possibilities
- let the user modify the result immediately

Celebration should support the creator's experience, not manipulate them into staying.

## Exploration

Users should be able to safely try ideas without constant fear of destroying the project or the surrounding system.

A safe experiment should feel like opening a new possibility, not pulling a dangerous lever.

## Growth

As users build more things, deeper concepts should become understandable through experience.

The ideal trajectory is from:

> “I can make things with this.”

toward:

> “I understand why this works.”

toward:

> “I can control how it works.”

## Finishing

Glyt should make shipping real software possible.

The tool should not treat distribution, packaging, execution, or public release as alien territory reserved for another language.
